# 接続方法とセキュリティ

**どう繋ぐか・どう守るか**を扱う。`architecture.md` が「層をどう分けるか」
という実装の話であるのに対し、こちらは接続形態とその安全化という運用の話。

本体（san-db-ox）の仕様書 §8 は「外部公開時には認証が一切存在しない点に
注意が必要である…具体的な接続方法・セキュリティ設定は本書の範囲外であり、
`san-db-ox-clients` のドキュメントで扱う」と明記している。**つまりこの
内容は本体が持たない機能の回避策ではなく、本体が明示的にこのリポジトリへ
委譲した責務であり、書く。**

このファイルは方針と判断根拠を書く。実際にコピーして使えるコマンド例は
`docs/`（フェーズ⑤で作成、`docs/usage/connecting_ja.md`）に置く。ただし
forced command の設定行だけは判断の核心そのものなので、ここにも具体例を
載せる。

## 直結（既定）— 同じトランスポートで届く範囲

`architecture.md` の「直結トランスポートは起動コマンドを差し替え可能にする」
とおりに実装すれば、以下はすべて同じコードで通る。

| 経路 | 起動コマンド |
| :--- | :--- |
| ローカル | `san-db-ox --serve-stdio` |
| SSH | `ssh user@host san-db-ox --serve-stdio` |
| Docker | `docker run -i --rm <image> --serve-stdio` |
| Kubernetes | `kubectl exec -i <pod> -- san-db-ox --serve-stdio` |

いずれもリモートコマンドの stdin/stdout を透過するだけであり、ドライバから
見た差は「起動するコマンドと引数が違う」ことだけである。

## SSH リモートコマンド直結（推奨経路）

`ssh user@host san-db-ox --serve-stdio` は、**socat も TLS 証明書もポート
開放も一切不要**で、認証と暗号化が SSH によって揃う。本体がネットワーク
待受を一切持たない設計（本体仕様書 §1・§10）を最も素直に活かせる形であり、
外部公開が必要な場面では第一に検討する経路として書く。

### `authorized_keys` の forced command

**認証・認可・接続元制限・読み取り専用の強制が、`authorized_keys` の
1行で揃う。**

```
from="10.0.0.0/8",restrict,command="/usr/local/bin/san-db-ox --read-only --serve-stdio" ssh-ed25519 AAAA... sandbox-readonly
```

- **`command=`** — この鍵で接続した場合、クライアントが何を要求しても
  このコマンドだけが実行される。**`--read-only` をサーバ側で強制できる**
  （クライアントの実装や善意に依存しない）。クライアントが送ろうとした
  コマンドは実行されず `SSH_ORIGINAL_COMMAND` 環境変数に入るだけなので、
  クライアント側は `ssh user@host` とだけ書けばよい（引数を送る必要も
  意味も無い）。
- **`restrict`**（OpenSSH 7.2 以降） — ポートフォワード・エージェント
  転送・PTY 割り当て・X11 転送等をすべて無効化する。この鍵では SanDBox に
  繋ぐこと以外できなくなる。
- **`from=`** — 接続元の制限（CIDR またはホスト名パターン）。

読み書き両方を許す鍵を発行する場合は `command=` から `--read-only` を
外すだけでよい。**読み取り専用の鍵と読み書き両方の鍵を、別の
`authorized_keys` エントリ（別の鍵ペア）として分けて発行する**運用を
基本とする——1つの鍵に両方の権限を持たせて呼び出し側の判断に委ねない。

### ドライバ実装上の注意

**SSH 自体の失敗（接続不能・ホスト鍵不一致・認証失敗等）は終了コード
`255` を返す。** リモートコマンド（`san-db-ox`）自身が `255` で終了した
場合と区別がつかない。ドライバは終了コードだけで「SanDBox 側のエラーだ」
と断定せず、stderr の内容と合わせて報告すること。

## socat 経由（ソケット）のセキュリティ

まず本体仕様書 §8 が定める前提を踏まえる。

- **接続ごとに別プロセス・別DBになる**（socat の `fork` オプションの挙動
  であり、SanDBox 自身の仕掛けではない）。1つの DB を複数クライアントで
  共有する用途には使えない。
- **認証が一切存在しない。** 到達できる者は誰でも任意の SQL を実行できる。
- **`overwrite` は使わない**（`architecture.md` 参照。複数の子プロセスが
  同じパスへ同時に書きに行くリスクがある）。

そのうえで、外部公開する際に検討する対策は以下の3つ。

### TLS/SSL による通信の暗号化

socat の `OPENSSL-LISTEN` アドレスタイプを使う。

```
socat OPENSSL-LISTEN:5432,fork,cert=server.pem,cafile=ca.pem,verify=1 \
      EXEC:"san-db-ox --read-only --serve-stdio"
```

**`verify=1`（既定値）によるクライアント証明書の検証（相互TLS）が、事実上の
認証機構になる。** `verify=0` にして暗号化だけ有効にすると、「盗聴はされ
ないが誰でも繋げる」状態になる——本体自身に認証機構が無い以上、これは
無防備な状態とほぼ変わらない。**`verify` を無効化しない。**

### 接続元IPアドレスの制限

- **`bind=127.0.0.1`** — ループバック限定で待ち受ける。もっとも安全で、
  後述の SSH ポートフォワードと組み合わせる前提の構成。
- **`range=<CIDR>`**（例: `range=10.0.0.0/8`） — 接続元を許可する
  アドレス範囲に絞る。
- **`tcpwrap[=<name>]`** — `/etc/hosts.allow` / `/etc/hosts.deny`
  （libwrap）による接続元制御と連携する。

**socat のオプションだけに頼らず、OS のファイアウォール（`iptables` /
`nftables` / クラウドのセキュリティグループ等）を最終防衛線として併用
すること。** socat の起動コマンドを1箇所書き間違えただけで公開範囲が
広がる、という事故はコマンドライン1行の設定にはつきものであり、外側に
もう1段の制限を持たせておく。

### `--read-only` との併用を前提にする

外部公開する SanDBox は、本体仕様書 §2・§9 のユースケース4（閲覧用デモ
環境の一時公開）が想定する形——**`--read-only` を必ず併用する**——を
基本の構成とする。書き込みを許す外部公開が必要な場合は、上記の TLS
クライアント認証と組み合わせ、かつ接続元を最大限絞ること。

## SSH のその他の使い方（補助）

- **ポートフォワード** — socat をループバック限定（`bind=127.0.0.1`）で
  立て、クライアント側から `ssh -L 15432:127.0.0.1:5432 user@host` で
  トンネルを通す。既にソケットトランスポートで書かれたコードをそのまま
  使いたい場合の手段。SSH が暗号化・認証を担い、socat 自体はループバック
  限定なので外部からは直接見えない。
- **`ssh -W`（ProxyCommand / stdio forward）** — SSH 自体に socat 相当の
  ブリッジをさせる形。上記2つ（リモートコマンド直結、ポートフォワード）で
  ほとんどの場面はカバーできるため、出番は限定的。
