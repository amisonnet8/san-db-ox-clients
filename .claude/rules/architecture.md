# アーキテクチャ

全言語のドライバが共有する構造を定める。新しい言語のドライバを書き始める
際は、まずこの構造に沿わせること。言語ごとに設計がバラけると、`protocol.md`
の契約を言語の数だけ別々に守ることになり、抜け漏れの温床になる。

## 2層に分ける

- **コーデック層** — JSON Lines の符号化・復号、値の表現（BLOB・REAL・
  64bit 整数、`protocol.md` 参照）、エラー応答の型付けを担う。**I/O もプロセス
  起動も一切知らない純粋な層**にする。パイプにもソケットにも依存しない。
- **トランスポート層** — バイト列の読み書きと寿命管理を担う。**この層は
  2種類しか作らない。**
  - **直結（既定）** — 子プロセスを起動し、stdin/stdout で対話する。
    どの言語でも最初に実装するのはこちら。
  - **ソケット（オプション）** — socat 等で外付けされた口へ TCP/UNIX
    ドメインソケットとして繋ぐ。本体仕様書 §8 の前提（接続ごとに別プロセス・
    別DBになる、認証が無い）がそのまま付いてくる。`connectivity.md` 参照。

コーデック層とトランスポート層は、互いに相手の型を知らない形にする
（コーデック層は `io.Reader`/`io.Writer` 相当のインターフェースだけを
要求し、トランスポート層の実装詳細に触れない）。

## 直結トランスポートは起動コマンドを差し替え可能にする

これが実装上もっとも重要な判断。「子プロセスとして何を起動するか」を
固定値ではなく**呼び出し元が指定できる値**にすることで、以下がすべて
同じ直結トランスポートで通る（`connectivity.md` 参照）。

- ローカル: `san-db-ox --serve-stdio`
- SSH: `ssh user@host san-db-ox --serve-stdio`
- Docker: `docker run -i --rm <image> --serve-stdio`
- Kubernetes: `kubectl exec -i <pod> -- san-db-ox --serve-stdio`

いずれもリモートコマンドの stdin/stdout を透過するだけなので、ドライバから
見ると差は「起動するコマンドと引数が違う」ことだけである。**SSH 専用・
Docker 専用の API やコンストラクタは作らない。** ドライバの API 表面積を
増やさずに接続先の広がりを扱え、その広がりの説明は `connectivity.md` という
ドキュメント側の役割にとどめる。

## 直結でしか成立しない API は型で区別する

子プロセスの stderr の内容、終了コード、`overwrite`（自身の実行ファイルを
上書きする op）は、ソケット越しの接続では意味を持たない。これらを共通の
インターフェースに混ぜ込まず、**直結トランスポートだけが持つ型**に置く。
「呼び出せるが実行時に失敗する」形にしないこと——コンパイル時（型のある
言語なら型チェックで、無い言語ならドキュメントとテストで）に、ソケット
接続からは呼べないと分かるようにする。

**`overwrite` は socat 経由で使わせない。** 本体仕様書 §8 が「複数の子
プロセスが同じパスへ同時に書きに行く」ため避けるよう明記している。上記の
型レベルの区別が、そのままこの制約の実装になる。

## コーデック層はネットワークに依存しないことを検証可能にする

本体の `make netcheck`（`net`/`net/http` を import していないことを CI で
機械的に確認する仕組み）と同じ発想を、可能な言語ではドライバ側にも設ける。
「層を分離した」という宣言だけで終わらせず、依存関係の検査で裏付ける。
