# プロトコル

**プロトコルの正典は本体（`san-db-ox`）の仕様書であり、このリポジトリでは
プロトコルの設計判断を行わない。** ここに書くのは、正典への固定リンクと、
それを各ドライバの実装チェックリストへ翻訳したものだけである。仕様の複製は
作らない——本体側で更新があったとき、二重管理で食い違うのを防ぐため。

仕様に不備・矛盾を見つけた場合は、まず本体の仕様書を直すことを提案し、
その更新を確認してからこちらの実装へ反映する。この順序を逆にしない。

## 追従先の固定

| 項目 | 値 |
| :--- | :--- |
| 本体リポジトリ | `github.com/amisonnet8/san-db-ox` |
| 追従しているタグ | `v0.1.0` |
| `protocol` 番号 | `1` |
| 正典 | 上記タグの `docs/spec/san-db-ox_spec_ja.md` §7（stdioプロトコル） |
| 補助 | 同タグの `docs/usage/stdio-protocol_ja.md` |

本体でプロトコルに関わる変更（op の追加、エラーコードの追加、`protocol`
番号の更新等）があったら、**まずこの表を更新してから**ドライバの実装へ
着手すること。「どのタグの仕様に追従しているか」が曖昧なまま実装を進めない。

## ドライバが必ず満たす契約

仕様書 §7 が「実装者への注意（本体・ドライバ双方の契約）」として明記して
いる事項を、ドライバ側の実装項目として書き直したもの。**「守らないと
動かない」契約**であり、利便性の話ではない。

- **hello 行を必ず読む。** 接続直後、最初のリクエストを送る前に
  `{"protocol":1,"version":"...","product":"SanDBox"}` が1行届く。
  `protocol` が自分の知らない番号であれば、それ以上通信せずエラーとする。
- **1リクエスト送るごとに必ずフラッシュする。** パイプはバッファリング
  されるため、これを怠ると本体・ドライバの双方が相手の入力を待ち続けて
  デッドロックする。
- **子プロセスの stderr を塞がない。** 読み捨てるだけでもよいが、必ず
  読み続けるか、そもそもパイプに繋がず `/dev/null` へ向ける。読まずに
  パイプへ繋いだままにすると、ログでバッファが埋まった時点で本体プロセス
  自体がブロックする。
- **EOF は接続断を意味する。** 検出して子プロセスの終了コードを回収する
  こと。回収しないとゾンビプロセスが残る。
- **`Close()`（等）は段階的に実装する。** stdin を閉じる → 一定時間待つ →
  まだ生きていれば SIGTERM、という順序が望ましい。
- 不正な JSON を送っても接続は切れない。エラー応答が1行返るだけなので、
  それを読んで次のリクエストを送ればよい。
- `id` フィールドは省略してよい。**応答は常にリクエストと同じ順序で返る**
  ため、`id` が無くても対応付けは可能。
- **64bit 整数を倍精度浮動小数点へデコードしない。** JSON の数値として
  正確に表現できる整数は 2^53 - 1 までであり、SQLite の INTEGER（64bit）の
  全範囲を表現できない。Go は `encoding/json` の `UseNumber()`（`json.Number`）
  で数値トークンを文字列のまま受け取り、必要になった時点で `strconv` で
  パースすること。
- **BLOB は1要素配列**（Base64、標準アルファベット・パディングあり・改行
  なし）。空の BLOB は `[""]`。**`params` でも同じ表現を受け付ける**ので、
  読み出した値をそのまま書き戻せる（往復の対称性）。要素数が1でない配列を
  受け取ったら実装のバグとして扱う。
- REAL は小数点付きで返る（`88.0`。`88` ではない）。NaN は `null`、+Inf は
  `9e999`、-Inf は `-9e999` として返る。
- 1行の上限は本体実装で 1 MiB。これを超える応答が来ることは想定しない。
- エラーコードは `sqlite_error` / `bad_request` / `io_error` /
  `unsupported_op` / `read_only` の5種のみ。**`message` の文言に依存した
  分岐を書かない。** 文言は変わりうるが `code` は変わらない。

## op 一覧

意味の説明は書かない（本体の仕様書を参照）。名前とパラメータ・応答
フィールドの索引としてのみ使う。

| op | パラメータ | 応答フィールド |
| :--- | :--- | :--- |
| `query` | `sql`, `params` | `columns`, `rows` |
| `exec` | `sql`, `params` | `rows_affected`, `last_insert_id` |
| `snapshot` | `filename`(省略可), `sqlite`(省略可), `timestamp`(省略可) | `path` |
| `load` | `path` | ─ |
| `inspect` | ─ | `has_data`, `version`, `data_length`, `source`, `read_only` |
| `tables` | ─ | `tables` |
| `schema` | `table`(省略可) | `schema` |
| `dump` | `pattern`(省略可、既定 `%`) | `sql` |
| `overwrite` | ─ | ─（応答後にプロセス終了） |
| `close` | ─ | ─（応答後にプロセス終了） |

エラー応答の形は共通: `{"ok":false,"error":{"code":"...","message":"..."}}`。

## こちら側で勝手に足さないもの

以下はいずれも本体が意図的に持たないと判断したものであり、**ドライバ側で
「あると便利だから」と再発明しない**（本体 CLAUDE.md・`protocol.md` が
継承する同じ判断）。

- `.import` 相当の op（CSV 等はクライアント側でパースし `exec` の
  `INSERT` を繰り返し送る）
- 任意パスを検査する `inspect`（`inspect` は自プロセスの状態のみ）
- 行を逐次取得するカーソル機構（`query` は結果セット全体を1レスポンスで返す）
- `iterate` 系のヘルパー（本体 CLAUDE.md が `engine` 側に持たせない理由と
  同じ——「書いていない解法が選ばれにくくなって実装者の視野を狭める」）
