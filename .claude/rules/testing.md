# テスト方針

## 本体バイナリの入手

- 既定は GitHub Releases から、`protocol.md` が固定しているタグ
  （現在 `v0.1.0`）のアセットをダウンロードし、併載の `.sha256` で検証する。
  ダウンローダは `scripts/fetch-san-db-ox.sh` 1本に集約し、全言語で共有する
  （フェーズ①で作成。shellcheck の対象になる）。
- **実行ビットは立っていない前提で `chmod +x` する。** GitHub Releases 経由の
  Linux/macOS 向けアセットは実行ビットが失われる（本体
  `.claude/rules/distribution.md` 参照）。Windows は `.exe` 拡張子で判定する。
- ローカル開発では `SAN_DB_OX_BIN` 環境変数でパスを上書きできるようにし、
  `go build` した手元のバイナリで確認できるようにする。

## ハングを失敗として検出する

**すべての読み取りにタイムアウトを設ける。** フラッシュ漏れ・応答の
取りこぼしは「無限に待つ」という形で現れるため、タイムアウトの無い
テストは CI を止める。本体 `tests/e2e.sh` が stdio の検証区間で、すべての
`read` に `-t 10`（10秒）を付けているのと同じ方針を、各言語のテストでも
踏襲する（Go ならコンテキストの `WithTimeout`、他言語もそれぞれの標準的な
タイムアウト機構を使う）。

## stderr をドレインしていることを担保する

**子プロセスの stderr を読み捨てる/破棄するコードが、実際に動いている
ことをテストで確認する。** 大量の stderr 出力（本体側の警告ログ等）を
吐かせた状態でもテスト対象の通信が詰まらないことを確認するケースを持つ。
`protocol.md` の契約のうち、ドライバ実装でもっとも踏みやすい罠。

## プロセスが確実に終了することを検証する

`close` op / stdin のクローズ / `overwrite` の3経路それぞれで、子プロセスが
確実に終了しドライバ側が終了コードを回収できることを確認する。孤児プロセス
が残ると、次回以降のテストがポート・ソケットの競合等でサイレントに壊れる
（本体 testing.md に同種の実例あり）。

## 値の往復を検証する

読み出した BLOB をそのまま `params` へ渡して書き戻せることを確認する
（`protocol.md` の「往復の対称性」）。2^53 を超える整数、NaN/±Inf を含む
REAL 値についても、送受信の往復で値が変わらないことを確認する。

## `--read-only` の検証

書き込み操作を `--read-only` で起動したプロセスへ送った際に、`read_only`
エラーコードで拒否されることを確認する。

## 接続方法のドキュメントは実測できるものだけを検証対象にする

本体の `tests/docs.sh` と同じ**オプトイン方式**（マーカーを付けたブロック
だけを実行し、機械的に実測検証する）を踏襲する。

- **ローカル直結の例は実測検証する。** devcontainer 内で本体バイナリを
  起動し、hello 行が読めること・簡単な `query`/`exec` が通ることまでを
  確認する。
- **SSH・socat・TLS・Docker の例は検証対象にしない。** 鍵・証明書・待受
  プロセスの用意が要り、CI 環境で毎回再現するコストが見合わない。本体の
  `docs.sh` も socat・Docker・ダウンロード手順の例には印を付けずに残して
  おり、同じ線引きになる。
- **検証できない例ほど、書いた時点で手元で一度実行して確かめること。**
  自動検証が無い分、記述ミスがそのまま残りやすい。`connectivity.md` の
  SSH forced command・socat のオプション名は、実際にコマンドを動かして
  確認してから書く。

## conformance スイートの実行

`conformance/` のケース定義を、各言語のテストランナーから読み込んで実行
する。詳細は `conformance/README_ja.md` を参照。

## shellcheck と trivy

本体と同じ方針で実施する。

- **`make shellcheck`** は `git ls-files '*.sh'` で追跡中のスクリプトを
  自動列挙する。新規スクリプトを追加しても Makefile 側の変更は不要。
- **`make trivy`** はローカル確認用。オプションは本体 CI と揃える
  （`--scanners vuln,license --severity HIGH,CRITICAL --exit-code 1`）。
  ライセンス方針も同じ——MIT/BSD/Apache-2.0 等は許可、GPL 系は拒否。
  ソースコード自体のコピペ検出は対象外（人間レビューに委ねる）。
- **CI では shellcheck・trivy のいずれも `ubuntu-latest` 限定の独立ジョブに
  する。** windows-latest に shellcheck がプリインストールされている保証が
  無く、内容も OS によって変わらないため、マトリクスで重複実行する意味が
  無い（本体 testing.md と同じ判断）。trivy も本体と同じく
  `aquasecurity/trivy-action` を使い、脆弱性 DB の鮮度を優先してパッチ
  バージョンまでは固定しない。
- **CI 定義（`.github/workflows/test.yml`）自体はフェーズ①のステップで
  作る**（初期構成には含めない。PLAN.md 参照）。

## シェルスクリプトを書く際の注意

**行頭を小文字の `# shellcheck` で始まるコメントにしない。** ShellCheck
自身がインラインディレクティブとして解釈しようとし、`key=value` 形式で
なければパースエラー（SC1072/SC1073）になる。大文字を混ぜて書けば
（`ShellCheck` 等）通常のコメントとして扱われる（本体で実際に踏んだ罠、
`postCreate.sh` を書く時点で当てはまる）。

## CI とローカルの接点

本体と同じく、CI の各ステップは `make <target>` の1語で呼び出し、ロジックを
YAML 側に書かない。
